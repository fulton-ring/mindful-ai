# Agent context and memory

Current implementation, verified against installed `@mastra/core` 1.67:

- D1 is the canonical transcript store. Messages expire after seven days of inactivity; approved notes remain. Thread deletion removes both.
- The main agent uses native `Memory` from `@mastra/memory`, backed by D1 and our `D1ObservationalMemory` extension of Mastra's D1 memory domain. The app transcript remains authoritative for UI, regeneration, interruptions, and expiry. Before each turn, the entire unexpired transcript is reconciled into native memory without reasoning text; unchanged messages retain their native metadata. Deleted or changed messages invalidate the observation generations before the corrected history is observed again.
- Native Observer/Reflector calls run over committed history before the main response, using the same explicitly configured Cloudflare model. The app keeps a soft 6,000-token tail of recent whole messages out of each observation pass using Mastra's public token estimator. The native Observer starts when the older eligible prefix reaches 12,000 estimated unobserved tokens, so a typical first compaction happens around 18,000 transcript tokens rather than at a fixed message count. A single large message can make the retained tail larger than 6,000 tokens. Reflection starts at 4,000 observation tokens. The actor receives observations plus the retained/unobserved messages through Mastra's native context assembly. The current user request and approved note are injected separately.
- Observation/reflection are awaited and background buffering is disabled. This first implementation may add latency to a threshold-crossing turn. The native manual observation API has no abort-signal argument, so a small model adapter forwards the request's signal to the provider for these calls. The 75-second turn deadline includes memory preparation. It does not rely on an untracked background promise for completion.
- Main-agent memory writes remain disabled at both the instance and per-run level. This prevents aborted/replaced responses from becoming a second transcript. Observations are produced explicitly with the public native engine API because Mastra's read-only processor does not automatically observe.
- Native observation lifecycle hooks drive the visible compaction state. The stream reports compaction only after Mastra starts an actual Observer call, and records a content-free checkpoint on the resulting assistant message only after that call succeeds. The checkpoint survives transcript reload through `activity_json`; observation text, provider metadata, and token counts are not exposed.
- Explicit thread deletion and both lazy/scheduled expiry remove the native thread and all observation generations. Preparation checks that the app thread is still active before and after observation, preventing stale work from retaining a deleted thread. Seven-day inactivity applies to raw transcript and generated observations; only approved notes remain.
- `buildTurnContext` injects the approved note and current request without duplicating native history. Secondary note generation still uses a 32,000-character recent-turn window. Notes are bounded to 48,000 characters; an oversized note is omitted whole, with exact edits disabled. Interrupted responses are marked and reasoning is not replayed.
- Native `TokenLimiter` caps each model step at 48,000 estimated tokens, including tool continuations. A small guard prevents silent loss of the current request or note context. Older supplied history is not incorrectly treated as required.
- Native `ToolCallFilter({ filterAfterToolSteps: 2 })` removes older tool call/result pairs from model-facing prompts while retaining the latest two tool-producing steps. It does not change stored/UI results. No per-tool token wrappers are used.
- The main agent is limited to five steps and one concurrent tool call. These bound execution; they are not compaction.
- Working memory, semantic recall, and automatic title generation are disabled. Observations are thread-scoped; there is no hidden cross-thread user profile.

## Native Mastra modules

`@mastra/memory` supplies the observation/reflection algorithms. We do not implement a separate compaction summarizer. The stock `@mastra/cloudflare-d1` 1.3.2 adapter lacks observational-memory storage operations, so `D1ObservationalMemory` supplies the native storage contract and advertises support. It is installed as `storage.stores.memory` before `storage.init()`.

The adapter stores native records in `agent_mastra_observational_memory`. It uses conditional SQL and a revision counter for read/modify/write operations, a unique lookup/generation index, atomic batches for buffered reflection activation, and parent-checked insertion. Late updates to deleted records fail. The app additionally enforces one streaming turn per thread with a D1 unique index. Buffering methods are implemented/tested for compatibility, but not enabled in production configuration. Durable background observation scheduling across Worker termination remains a separate future step.

The native `TokenLimiter` and `ToolCallFilter` still bound model-facing context and tool history. They trim context, not the stored transcript. Observations are not approved notes and cannot write into the user's note editor.

Sources: [TokenLimiter](https://mastra.ai/reference/processors/token-limiter-processor), [ToolCallFilter](https://mastra.ai/reference/processors/tool-call-filter), [tool output mapping](https://mastra.ai/docs/agents/tools), [observational memory](https://mastra.ai/docs/memory/observational-memory), [D1 adapter](https://mastra.ai/integrations/databases/cloudflare-d1).

## Filesystem

The primary agent can attach native `Workspace` + `S3Filesystem` backed by Cloudflare R2. Configuration requires R2_ACCOUNT_ID, R2_BUCKET, R2_ACCESS_KEY_ID, and R2_SECRET_ACCESS_KEY. Access is scoped to an encoded owner/thread prefix and read-only; approved note writes continue through the review/accept flow. With no R2 config, no filesystem tools are advertised; partial config fails explicitly. R2 credentials and a bucket have not been provisioned or tested. See runbooks/credentials.md.

## Browser and source retrieval

The main Mastra agent exposes direct `readWebPage` and `searchSources` tools when a complete research transport is configured. Code Mode is not used. With `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`, both Browser Run and AI Search use their authenticated REST APIs; native `BROWSER` and `AI_SEARCH` bindings are the fallback when REST credentials are absent. Browser Run returns rendered Markdown; only that fetched content is indexed, not private notes or transcripts. AI Search queries are always filtered by the server-derived owner scope and returned metadata is checked again. Results preserve validated source URLs for Markdown citations. Upload is queued rather than waiting for indexing; new content may not immediately appear in search. The page content is available to the agent immediately.

The source index is separate from seven-day conversation/observation retention. Retrieved public pages are reusable across the same user's threads; deleting a thread does not delete these cached sources. Page content is capped at 12,000 characters in a tool result and 64,000 indexed characters; searches return up to five 4,000-character passages. Timeouts, request cancellation, same-origin browser request filtering, and response-size bounds limit tool work. Website instructions cannot override agent policy.

Local research uses the `research` Wrangler profile with local workerd and the private `mindful-ai-sources` instance in the `default` namespace. REST transport avoids the unavailable edge-preview path (code `10023`) and does not require Wrangler login. A real Chrome run verified page reading and a queued indexing acknowledgement; search retrieval through the running browser app remains unverified. See `runbooks/research.md` for startup and verified limits.
