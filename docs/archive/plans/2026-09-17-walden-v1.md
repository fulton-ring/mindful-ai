# Walden V1 Implementation Plan

> **For agentic workers:** Use the executing-plans skill to implement this plan task-by-task. Steps use checkbox syntax for tracking. This is a proposed architecture and delivery plan for review, not authorization to deploy or charge customers. Expand each milestone into implementation patches against the package versions pinned in Task 1.

**Goal:** Build a notes-first AI workspace that helps people articulate their own thinking, with temporary conversations and explicit user control over what becomes durable.

**Architecture:** One React client, one TypeScript API/agent service, and one application database. Markdown notes and authorship metadata are authoritative; chat and pending suggestions are temporary. The agent proposes changes, while authenticated, revision-checked application operations perform them.

**Tech stack:** pnpm workspaces with Turborepo, Biome for linting/formatting, TypeScript, React/Vite, TanStack Router/Query, Tailwind/shadcn, CodeMirror 6, Mastra, AI SDK UI, Hono, Cloudflare Workers with static assets, D1/Drizzle, hosted authentication (Clerk proposed), Stripe, Vitest, Playwright. Jeremy agreed with the recommended direction and explicitly requested Turborepo and Biome on 2026-09-17; auth, pricing, and other product defaults below remain proposals.

## 2. Proposed decisions to review

1. **Retention — confirmed by Jeremy:** expire the transcript after seven days of inactivity, measured from the last accepted user message. Opening a conversation, editing notes, or receiving assistant/tool output does not extend it; sending a user message before expiry resets the deadline to seven days later. Notes remain durable. On expiry, a new conversation can use only saved notes and explicitly selected settings. Nightly clearance is not used.
2. **Workspace:** multiple named notes documents; one selected at a time. Each has at most one active conversation in V1. App opens on the last selected notes, with chat closed, even if a conversation still exists.
3. **Stack:** Mastra/TypeScript on Cloudflare, rather than Pydantic AI/Python on GCP. This keeps one language across UI, schemas, stream events, and tools. A Node/Mastra service on GCP Cloud Run is the fallback if the Workers integration spike fails. Pydantic AI/GCP remains reasonable if Python is a strong preference, at the cost of a second language and contract generation.
4. **Editor:** CodeMirror with plain Markdown and decorations. It directly suits a text document with insertion previews. A rich-text editor adds Markdown round-trip and provenance complexity; a textarea lacks reliable inline decorations and transaction mapping.
5. **Auth — requirements confirmed by Jeremy:** support email and Google login without storing credentials in the application database. Proposed email method: passwordless one-time code. Use hosted authentication; Clerk is the current recommendation for public customer signup, subject to the integration spike. Cloudflare Access also supports email OTP and Google and is a valid option for a gated pilot or private/admin applications; its public signup, identity lifecycle, and commercial fit would need evaluation before choosing it for all customers. This replaces the Better Auth/D1-backed auth proposal. Provider selection is not yet confirmed.
6. **Pricing proposal:** $9/month personal, no annual/family/lifetime plan in the first release. Free gets 10 successful assistant turns/day; paid gets 500/month with a clearly displayed reset. These are validation defaults, subject to the cost benchmark, not numbers supplied by the spec. Notes remain editable/exportable when chat reaches its limit.
7. **MCP scope:** one real, operator-configured remote HTTPS read-only connector at launch, plus a test server exercising reversible/irreversible actions. User-configured servers and real send/booking integrations follow separately. This is a proposed bounding of the spec's otherwise open-ended MCP substrate.
8. **Model — confirmed by Jeremy:** Cloudflare Workers AI with `@cf/google/gemma-4-26b-a4b-it`. Use the native AI binding through a compatible AI SDK provider. No multi-provider selector or commercial-model fallback in V1. Run the behavioral checks against this model; switch only with a subsequent product decision.
9. **Pilot:** adults doing their own writing/thinking; education-style examples are supported without assuming child accounts or a parent administration product.

These decisions allow planning to continue; they should be reviewed before their dependent milestone is implemented.

## 3. Product rules that code must enforce

### Notes and capture

- Agent-generated text cannot enter persisted notes without an explicit user action. Saying “put that in the notes” creates a proposal; it does not accept the wording.
- A ghost is a decoration, not part of the Markdown value, autosave, export, search, or future model context. It never steals editor focus.
- Tab accepts only when the editor is focused at the active proposal. Provide an accessible button/touch equivalent. Elsewhere Tab retains normal navigation behavior.
- Typing at the proposal clears it before inserting the user's input. Typing elsewhere only maps its position. Handle IME composition, paste, undo, and touch keyboards deliberately.
- Escape/dismiss clears the proposal. An ignored proposal expires when the next user message advances the conversation; typing elsewhere alone does not count as advancing the conversation. It never reappears on pause.
- At most one pending intervention across ghost text, ASK, RECORD, and a learning check. Explicit new user requests may replace it; unsolicited ones cannot queue behind it.
- Propose only a decision, a surfaced constraint, a load-bearing number, or a user-requested capture. A generic “anything to record?” prompt is forbidden.
- ASK presents 2–4 concrete choices plus Other. Selecting one is the explicit save action and writes the chosen decision; mark the interaction `user_choice`, while retaining `agent_verbatim` wording if the supplied option text was unchanged. Choice alone is not own-words writing.
- RECORD defaults to “Put it in my words,” with Ask about this, Record as-is, and Dismiss. Rewrite drafts remain unsaved until submitted. Asking about it resumes discussion without accepting the text.
- Accepted unedited agent wording remains a lighter shade. Editing a word changes the line to normal ink, as the board specifies. Whitespace-only or punctuation-only changes should not satisfy that rule. Undo restores both text and marking.
- Keep origin and current presentation distinct: an edited AI line can be normal ink while retaining `origin=agent` in internal metadata. No semantic claim that editing demonstrates learning.
- The debt line counts current, still-verbatim accepted captures from this session, not paragraphs inferred by the model. Deleting, editing, or undoing a capture updates it. No skipped-intervention counter.
- After dismissal, suppress the same candidate in the current conversation. A new topic/decision may create a different candidate; merely paraphrasing a rejected line does not.

### Posture and response behavior

Use a small typed policy state, not a free-form hidden personality switch:

| Situation | Allowed behavior |
| --- | --- |
| Producing/thinking through a deliverable | Direct help; no knowledge quiz. Ask an artifact clarification only when its answer fills a concrete part of the artifact. |
| Consuming/summarizing | Direct answer; optional, skippable restatement offer. No forced quiz. |
| Explicit learning request | Forward-facing checks at natural seams, normally 2–3 across a lesson, never a per-turn quota. |
| Ambiguous | Direct help without a quiz. |
| User says stop checking or changes to production | Immediately revoke learning-check eligibility. |

The active persona is always labeled. While learning consent is active, show a quiet “Learning checks on” control so inferred posture cannot become invisible persistent state. Persona settings never override capture consent, ownership, retention, or action safety.

Every check names a concrete target and receives specific feedback: what was right, what needs correction, and a useful next step. Skipping does not gate the answer or penalize the user. Ordinary learning answers stay in the temporary conversation; turning them into notes still requires the capture path. An artifact answer is saved only through an explicit submit-to-notes interaction.

### Transcript lifetime

Calculate expiration with server UTC timestamps. Enforce expiry on every read, generation, retry, and tool continuation, not only in scheduled cleanup. Expired conversations return no messages and cannot be resurrected by delayed streams. Cleanup purges messages, annotations, pending interventions, unaccepted drafts, and tool payloads. Purge client query state on expiry/sign-out; do not persist transcripts in localStorage or a service-worker cache.

No framework long-term memory, embeddings, transcript summaries, or background retrieval in V1. Durable note content and selected persona/settings are the only carry-forward inputs. Accepted notes may preserve their text and source URL; they must not retain a hidden copy of the originating transcript.

Database backups, model-provider retention, and gateway traces need separate policies. D1 Time Travel retains recoverable history after a SQL delete; therefore promise expiry from the live product, and document backup/provider retention accurately. If the intended promise is unrecoverable deletion at the exact deadline, reconsider storage/encryption before launch. Restore procedures must reapply expiry before serving traffic.

### Data model

| Entity | Required data / rule |
| --- | --- |
| App user | Internal ID, unique auth issuer/subject reference, minimal display profile, timestamps. No credentials or provider session tables. |
| Note | ID, owner ID, title, Markdown, revision, current provenance spans, created/updated timestamps. Text plus spans update atomically. |
| Note edit | Unique operation ID, base/result revision, origin, inverse edit and inverse spans. Scope to the note owner; bounded 30-day undo history as a proposal. No rejected AI text. |
| Conversation | Owner, note ID, last user activity, expiry, selected persona version; lifecycle active/expired. |
| Message | Conversation, turn ID, role, content, completion status, sequence. Only completed/explicitly retained partial output participates in future context. |
| Intervention | ID, conversation/turn ID, kind, reason, note base revision, proposed text edit or card payload, status. Unique pending slot per conversation. Expires with conversation. |
| Persona | Owner, name, prompt, tone/brevity/challenge settings, revision. Snapshot selected revision per turn. |
| Tool execution | Owner, connection, request ID, effect class, confirmed argument hash if required, execution state, compensation info. Content payload expires with chat. |
| Entitlement / usage | Customer/subscription mapping, plan, period, reserved and consumed units, idempotency key. No message bodies. |
| Product session | Session ID, user ID, selected note, starts-from-existing flag, own-words-change flag, timestamps. No prose or keystroke capture. |

Use `owner_id` checks on every query, including children joined through conversation/note. Never authorize via a client-supplied user ID. Every write and stream has a server-side authenticated principal. Resolve the verified auth issuer and subject to the internal user ID; never use email as the ownership key.

### Authentication and credential boundary

- Hosted auth handles email-code delivery/verification, Google OAuth, account linking, session issuance, logout, and recovery. Do not create password, password-hash, OTP, magic-link-token, refresh-token, OAuth-token, or session-token columns in D1. Product-session metrics are not authentication sessions.
- API middleware verifies provider-issued authentication with the supported server verifier, checking signature, issuer, intended audience/authorized party, and expiry. Do not trust an email header or browser-provided user ID. Validate revocation/logout behavior during the spike.
- Require provider-verified identity linking when a user signs in by email and later Google; do not automatically merge app users based on an email string. Test that supported linking preserves notes and billing ownership.
- Email code entry and Continue with Google are both available on signup/sign-in. Handle expired/reused codes, resend limits, cancelled OAuth, and session expiration without losing note drafts.
- Provider client secrets, API keys, and webhook signing secrets live in Workers secrets or an appropriate secret manager. Provider-hosted user authentication data stays outside D1. Connector credentials also stay outside D1: use a dedicated credential vault/broker and store opaque references only; operator-configured V1 credentials can use Workers secrets.
- Retire the earlier proposed Better Auth-managed `/api/auth/*` routes. Login uses the hosted provider flow; the app can expose authenticated `GET /api/me` for its own profile/entitlement summary. Add a signed provider lifecycle webhook only if needed for identity deletion/synchronization.
- Account deletion must delete the hosted identity as well as application data, with retryable cleanup and tests for partial failure.

### Note editing protocol

`PATCH /api/notes/:id` accepts `{operationId, baseRevision, changes, provenanceChanges}`. Each change has `{from, to, insert}` in UTF-16 document offsets; changes are nonoverlapping and relative to the supplied base revision. The server validates ranges and permitted provenance transitions, then atomically compares the revision and saves text, spans, and inverse operations. Client-supplied author labels are not blindly trusted.

- Successful save returns `{revision, operationId}`.
- Repeated operation ID returns the original result without applying twice.
- Stale revision returns `409` with the current revision; client retains its unsaved draft and offers comparison/retry. Never overwrite the remote note automatically.
- Note ownership mismatch returns `404`; invalid input `400`; unauthenticated access `401`.
- Start with one writer per note and optimistic concurrency. Do not add CRDTs or collaborative cursors.

**Editing approach — clarified with Jeremy:** reuse the established coding-agent pattern: read document → tool proposes a targeted text edit → display inline diff → accept/reject → save. Do not build a semantic anchor language, custom diff engine, or separate fast-apply model.

Use a small `propose_note_edit({noteId, baseRevision, oldText, newText})` tool. Require `oldText` to match exactly once in the base snapshot. Insertions include a unique neighboring passage in both old/new text; deletions replace a nonempty passage with an empty string. Empty `oldText` is allowed only when the entire note is empty. Missing or ambiguous matches return a tool error to reread/retry. The agent does not produce offsets. This is a search/replace edit tool in the same broad family as coding-agent patch tools, not a claim that Cursor and Codex use identical formats.

Use the existing `diff` (jsdiff) package for text differences and CodeMirror transactions/decorations for inline presentation. Keep the adapter small. Codex's `apply_patch` dialect is a different format from standard unified diffs; do not assume jsdiff parses it. Our initial tool uses old/new text and avoids that dependency entirely.

For a one-line addition, display the existing ghost-text UX. For replacement/deletion, display an inline before/after suggestion with accept/reject controls and typography consistent with the notes surface. Pending edits exist outside saved Markdown. Acceptance saves through the existing revision-checked protocol and records provenance plus undo. Map across unrelated local typing; invalidate on overlap or remote revision conflict and request a fresh proposal. No fuzzy application to changed text.

### Streaming and agent boundary

`POST /api/chat/turns` accepts `{requestId, conversationId, noteRevision, message, personaId}`. Flush pending note saves first; on conflict, keep chat input and resolve the note instead of generating against stale content. The server loads authorized note context and unexpired conversation history, reserves quota atomically, snapshots persona, and starts one turn.

Stream assistant text plus validated typed data parts: `status`, `annotation`, `intervention`, `usage`, `error`. Every part is scoped to a turn and conversation; the client ignores obsolete parts. Unknown/invalid intervention data is dropped without breaking readable assistant text. Never parse application commands out of arbitrary Markdown.

Mastra handles model orchestration and tools; AI SDK handles the UI stream protocol. Application code owns message persistence, expiry, policy decisions, and note mutation. Disable framework persistence of raw prompts/responses by default. Limit each turn's tool steps, tokens, wall time, and one concurrent generation per conversation.

Cancellation saves an explicitly incomplete state and reconciles incurred model usage. Do not retry a completed external action when reconnecting. Repeated request IDs reuse the existing turn outcome. Expiration invalidates a stream before any subsequent mutation.

### MCP policy

MCP is a client capability of the server, not a reason to expose all notes through a public MCP server. Use remote HTTPS transport and operator-allowlisted endpoints. Credentials stay server-side and are scoped per user/connection. Treat tool descriptions, results, and notes as untrusted content that cannot override system policy.

Do not confuse idempotence with reversibility. Classify effect as read-only/reversible/irreversible and track retry safety separately. Application configuration controls classification; server annotations are hints.

- Read-only: execute within the user's requested task.
- Reversible: execute and register a real inverse/compensation operation; show Undo.
- Irreversible or unknown: show one concrete confirmation with destination, arguments, consequence, and cancellation path if one exists. Bind approval to that exact call; parameter changes invalidate it.
- Notes still require the capture interaction even though editing is reversible: the explicit “nothing crosses the seam” rule takes precedence.
- Protect connection setup against private-network endpoints/redirects; cap tool response size and duration. Never forward arbitrary note context to unrelated tools.

## Product correction — September 18, 2026

The entry point is chat. Users create notes while chatting, or explicitly accept a capture into a new note. Starting or sending a conversation must not create an empty/hidden note. A conversation may have no note; linking or removing its note preserves the transcript. Deleting a conversation leaves saved notes intact.

TanStack Query owns persisted conversation list/detail state, as well as notes. Create, delete, and note-link mutations update or invalidate the relevant cache entries. Local component state is limited to selection, draft text, streaming output, and other transient UI state. Deleting the selected conversation returns to a fresh chat without requiring a reload.

All changes from this correction are developed and evaluated locally. Remote deployment requires a new explicit user instruction.
